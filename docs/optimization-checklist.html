claude-web 优化清单

基于代码审计（daemon、server、frontend、安全），按严重度排序，标注位置和修复方案

统计：共 28 项问题。CRITICAL 4 项 / HIGH 7 项 / MEDIUM 10 项 / LOW 7 项
重点区域：daemon 进程鲁棒性、server.py 事件循环阻塞、前端 DOM 无限增长、移动访问模式下的 CSRF
原则：我们的架构（持久 Node 守护进程 + 8 并发 runtime + 4字节帧协议）比竞品好。问题在细节打磨。

一、Node 守护进程 (daemon.mjs + agent_sdk_bridge.py)

严重度问题位置影响 / 用户感知修复方案
进程鲁棒性
CRITICAL 无 uncaughtException / unhandledRejection 兜底 daemon.mjs 全文 SDK 任何未捕获异常直接杀死 daemon，所有 8 个活跃会话全挂 加 process.on('uncaughtException/unhandledRejection')：终止当前 turn + 写 error+done，daemon 继续存活
CRITICAL 无 process.exit() 拦截 daemon.mjs 全文 如果 SDK 内部或依赖包调 process.exit()，daemon 无预警死亡 覆盖 process.exit = (code) => { throw new DaemonExitInterrupt(code) }，在 handle() 外层 catch
HIGH 无 PPID 孤儿监控 daemon.mjs 全文 Python 被 kill -9 / OOM 后，daemon 变僵尸永不退出，占端口和内存 setInterval 每 5 秒检查 process.ppid，变为 1 或 ESRCH 就 graceful shutdown
并发与竞态
CRITICAL abandon_turn 先删 queue 再发 interrupt，done 帧被丢弃 agent_sdk_bridge.py:390-394 后续该 session 所有 turn 失败："A Code turn is already running"，持续 30 分钟直到 idle 回收 先发 interrupt → 等 done 到达（带超时）→ 再删 queue
CRITICAL interrupt 和 readRuntime write() 竞态 daemon.mjs:417-448, 613 interrupt 返回 ok 但 turn 不出 done 帧，session 挂起 interrupt 时先设 aborted flag → readRuntime 循环检查 flag → 确保 done 一定发出
HIGH preflightSend 和 handleSend 之间有时间窗口可被并发 send 穿越 daemon.mjs:586-604, 869 同 session 两个 turn 都收到 accepted，事件互串，session 损坏 将 preflightSend + accepted + handleSend 合为单个原子操作，在同一个 withRuntimeMutation 内完成
MEDIUM idle 扫描 disposeRuntime 未 await，旧 reader 可能写已被复用的 requestId daemon.mjs:888-893 极低概率下新 turn 收到旧 runtime 的事件 await disposeRuntime 或在 dispose 前先 detach activeRequestId
资源泄漏
MEDIUM permissionWaiters 在 queue overflow 时泄漏（30 分钟 timer） daemon.mjs:269-270 内存缓慢增长 + 可能 double-resolve queue overflow 时同步清理该 session 所有 pendingApprovals + permissionWaiters
MEDIUM _responses future 超时后 reader 调 set_result 抛 InvalidStateError 杀死整个 reader agent_sdk_bridge.py:396-406, 280 极低概率但致命：reader 死后所有 session 无法收到事件 reader 内 set_result 包 try/except InvalidStateError
延迟优化
HIGH 无 preconnect 预热，首条消息承受 2-5 秒 SDK 冷启动 daemon.mjs handle() 用户创建 Code 会话后发第一条消息要等很久 新增 method:'preconnect'，Python 在创建会话时即调用，提前创建 runtime
MEDIUM 无 turn 间事件监听（perpetual reader） daemon.mjs readRuntime() 子 agent 后台完成后用户无通知，要等下次交互才看到结果 turn 结束后保持 query.next() 循环，收到事件通过新消息类型 push 给 Python
LOW shutdown 2 秒超时经常不够，graceful close 被跳过 agent_sdk_bridge.py:611-617 进程重启时 SDK 连接被粗暴断开 增大超时到 5 秒，或按 runtime 数量动态调整
